## Findings

- High-cardinality integer grouping runs in about 1.12 s at one worker and 1.14 s at eight. The profile has 5.87 s sampled CPU over 5.83 s wall time, about one active core; u64Index.get accounts for 65.25% flat CPU. The two-aggregate plan is rejected by execution_parallel.go:82-85, which supports one aggregate boundary, and falls back to serial execution.
- COUNT DISTINCT at eight workers improves only 1.09x over four workers on balanced ten-million-row input. Its profile spends 47.58% flat CPU in lookupString plus lookup; mergeDistinctSet accounts for 29.39% cumulative CPU. These percentages overlap and must not be added.
- The eight-worker grouped report profile uses about 7.83 cores on average; groupState.add accounts for 61.86% cumulative CPU and selected string materialization for 21.06%. The groups include string keys and multiple reductions. Those cumulative costs include child functions.
- On balanced ten-million-row input, peGosus ordinary aggregates and join reports improve 6.63-7.16x from one to eight workers, but their eight-worker timings still trail DuckDB and DataFusion.
- The 32 failures are all peGosus ErrorResourceExhausted outcomes across 16 unique configurations, each reproduced in two rounds. No competitor query failed. This harness disables peGosus spill execution; output accounting and native budgets differ between engines.
- At eight workers on balanced ten-million-row COUNT DISTINCT, peGosus cold sampled RSS is 2486.6 MiB versus DuckDB 611.2, Polars 1070.5 and DataFusion 1461.3. Final peGosus live payload returns to zero, but reusable capacity and process memory remain high. The 1 GiB query budget is not an RSS cap.
- The ten-million-row grouped report stays small in peGosus (38.2 MiB cold sampled RSS at eight workers), versus DuckDB 85.8, Polars 1696.2 and DataFusion 248.3. Memory behavior varies substantially by query.

The three diagnostic CPU profiles are excluded from comparison sample counts and timings; their output fingerprints also match the matrix. Raw profiles persist under ignored testdata/cross-engine-followon/.

## Next priorities

3. Measure dictionary-preserving grouping and scalar/key-encoding overhead, then factorized join-to-aggregate execution. Extend spill composition and benchmark explicit spill and streaming output separately from this no-spill retained-result matrix.

## Interpretation limits

- Warm-cache synthetic fixtures; these are not production datasets, an official benchmark score, or universal engine rankings.
- Two reversed-order rounds; timings are pooled medians of ten samples per engine/case/query/worker setting. Failed queries are excluded entirely from timing rankings.
- peGosus Prepare is excluded; DuckDB execute includes SQL planning, Polars collect includes optimization, and DataFusion includes SQL planning and Arrow collection.
- DuckDB fetchall converts outputs to Python rows inside timing; peGosus returns owned results, Polars native DataFrames and DataFusion Arrow batches. Large-output timings are adapter-inclusive.
- Output release is excluded from execution timing and available separately in raw reports; result fingerprints are outside timing windows.
- peGosus and DuckDB use a 1 GiB query budget. peGosus spill execution is disabled here; DuckDB and DataFusion may spill, and Polars has no equivalent configured hard budget.
- Worker settings differ by runtime and are not a strict OS thread quota. The desktop CPU uses its existing governor and adaptive boost.
- Linux sampled RSS peaks are lower bounds. Cold growth is relative to the immediate pre-query RSS, which can differ from ready/startup RSS. Exact endpoint RSS/PSS, scope payload bytes and retained allocator capacity are separate metrics.
- Numeric fixtures use dyadic values and exclude NaN/Inf/rounding stress; package tests, not this matrix, cover those semantics.

Raw samples, release timings, round medians, checksummed fixtures, exact RSS/PSS endpoints, commands and full source/binary provenance are retained in the matching JSON reports.
